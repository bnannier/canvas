# Platform reference catalog

The canonical design reference for every Canvas component on **iOS**, **Android (Material 3 /
Jetpack Compose)**, and **Web**. This is the source each platform skin is matched against.

**iOS source of truth: the [Apple iOS 27 UI Kit](https://www.sketch.com/s/04c24d8b-38fb-4afb-8836-36617e022f02/symbols)**
(Apple's official design resource, published as a Sketch library). Each iOS link below opens that
kit's symbol group, with pixel-accurate Light and Dark renders of the real control. Apple HIG text
pages are kept only where the kit has no symbol for the control. Note for tooling: the kit renders
in a browser session (its images are signed and cannot be hotlinked or WebFetched), so agents that
need the iOS spec must screenshot the group in a browser, or read the extracted spec notes.

**Android source of truth: the [Material 3 components catalog](https://m3.material.io/components)**
(m3.material.io). Each Android link below opens that catalog's component overview page, including
the M3 Expressive updates: connected button groups replace segmented buttons, the loading
indicator replaces the indeterminate circular progress indicator, and docked toolbars replace the
bottom app bar. The Jetpack Compose API docs (developer.android.com) remain the implementation
reference, not the design reference. Note for tooling: m3.material.io is a JS app whose pages
cannot be WebFetched; read them in a browser session, and verify URLs against
https://m3.material.io/sitemap.xml.

Canvas is **platform-forward**: the brand survives (Dark Factory's palette, with its violet
`primary` and green `action`, and the Manrope type stay the same on every platform); only the
native shape, sizing, structure, and interaction feedback change per OS. React Native does not provide these looks for free (its primitives are unstyled and its
core `<Button>` is unusable), so each control's per-OS appearance is hand-written, EXCEPT the few
real native widgets RN ships (`Switch`, `ActivityIndicator`), which can be used natively and
branded via props.

**Treatment** column, read off the code (what each platform build draws, per
`tools/skins/divergence.ts`):

- **Full**: the component's own skin differs per platform: distinct iOS / Android / Web
  skins, matched to the references below.
- **Light**: the component's own skin differs per platform in small touches (radius,
  density, type, shadow) over one structure.
- **Shared**: the component's own skin is the web skin on every platform. A platform part
  it injects (the platform's Button, Dropdown or Checkbox) may still differ; the part
  answers to its own row.
- **Missing**: in the iOS 27 kit but not yet a Canvas component (build backlog).

Every docs component has a row, the primitives and layout components included. A
component keeps a native shape only on a platform whose cell cites a control for its job
(design-language item 3 in `CLAUDE.md`); where the cell is a none note, its native skin is
the web skin. `test/platform-references.test.ts` holds the table to the code: Treatment is
Shared exactly when no platform builds a skin of the component's own, and a native skin
of the component's own stands under a none note only as a recorded one-job substitute (the
different control that platform uses for the job, such as the iOS switch for a Checkbox)
or as a transitional skin naming the audit turn that aliases it. A cell that cites a
control where the component draws the web skin stands only with the recorded reason no
native shape is owed there (a hairline Divider, the kit's own glyphs, a primitive that is
the platform's own view).

**Build** column: "Built" for shipped components; backlog rows carry a researched Yes/No verdict.
A backlog component is built only when ALL five criteria hold:

1. **Platform reach**: a real, documented control on at least 2 of the 3 target platforms, or an
   essential single-platform idiom whose absence makes apps feel non-native there.
2. **In-app renderable**: Canvas can draw it with React Native primitives; OS-rendered surfaces
   (system keyboards, OS chrome) fail this even though apps can invoke them.
3. **Not already covered**: no shipped component or trivial composition covers the role; a
   variant or prop on an existing component is preferred over a new component.
4. **Universally feasible**: implementable and maintainable in React Native AND React Native
   Web (gestures, accessibility, performance), as proven by peer universal kits.
5. **Demand**: evidence apps need it: Canvas v2 shipped it, peer kits (shadcn, Catalyst,
   Material 3, gluestack, NativeBase) ship it, or it is a standard form/navigation primitive.

A cell marked `(none: ...)` states plainly that the platform has no such component, and why;
nothing is linked in its place, and lookalike controls are named in words only (e.g. iOS has no
checkbox, radio, or wizard stepper; Material 3 has no stepper or pagination). The kit's "Stepper"
is the iOS +/- increment control (Canvas `stepper`), NOT the multi-step wizard (Canvas `steps`);
they are separate rows.

## Text entry

How a kit text field (Input, Textarea, PhoneInput, Autocomplete, InputOTP) says whether it can be edited, on each platform. The kit fields share one helper, `src/style/text-entry-state.ts`; the raw TextInput primitive takes React Native's own props, and the same recipe applies to it.

- **Disabled** is `editable={false}` with `aria-disabled` and `accessibilityState.disabled`. The web renders the native `disabled` attribute and `aria-disabled`, so the field leaves the tab order and takes no focus. iOS and Android receive `accessibilityState.disabled`, so VoiceOver and TalkBack announce the field as dimmed, an iOS multiline field (Textarea) included, which `editable={false}` alone does not dim.
- **Read-only** (`readOnly` on Input and PhoneInput) is `editable={false}` alone. The web renders the `readonly` attribute: the field stays in the tab order and its text stays selectable. React Native's TextInput has no read-only mode: it maps `editable={false}` to a disabled native view (`setEnabled(false)` on Android, `enabled = NO` on an iOS single-line `UITextField`). So on iOS and Android a read-only field is announced as dimmed, like a disabled one, and its text cannot be selected on Android. Matching the web there would take native work outside React Native's TextInput API; the kit documents the platform's behavior instead.

## Glass material

What `<ThemeProvider glass>` renders on each platform, and where it renders the complete solid skin instead. One decision (`useMaterialResolution`, `src/style/glass-surface/use-material-theme.ts`) answers it for a surface, its GlassPane and the host that paints around the pane, so a host that keeps its solid skin never has a pane painted inside it.

- **Web**: Dark Factory's plain frost (a 24 px backdrop blur, the layer's tint, a 1 px inset hairline) in every browser that renders a CSS backdrop filter; a browser without one renders the solid skin.
- **iOS**: Liquid Glass through `expo-glass-effect` on iOS 26 and later for a surface that is not static (the functional layer, controls, dense overlays); `expo-blur`'s frost for a static surface (the content layer, text-entry wells) and wherever Liquid Glass is unavailable. A surface whose material's peer is not installed renders the solid skin.
- **Android in the page: solid, by design.** With `expo-blur` 57 or later (its blur target) or the `@nannier/canvas-blur` capture integration, Android's frost samples a separate capture plane, and only an overlay in an OverlayProvider outlet or a sheet in a window of its own has one it can sample without capturing itself. A surface in the page itself resolves solid (`missing-target`) and keeps its complete solid skin, so the audit's Android glass column equals solid outside overlays. Frosting in-page surfaces would take a page-level capture plane: separate native work, with a tuning-harness card of its own.
- **Android overlays**: the frost, over the outlet's or the window's own plane.
