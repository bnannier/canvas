The component audit captures interaction states and pages, and analyzes, sheets and indexes every capture. `bun run audit:web -- --states` hovers, focuses (with the Tab key), presses, opens, and finds invalid and disabled each component the interaction registry lists, as far as it has those states, through one recipe table that names each state's example (a state a component shows in more than one place has a recipe for each, its cells named for their examples: Dropdown's disabled trigger, and the disabled item inside its menu), verifies the state from the page before photographing it (the hover's lift or wash, `:focus-visible` and the ring in the pixels on every side, the pressed style against the hovered one, a chart's value flag or readout under a press, the opened panel and where it painted, `aria-invalid`, `aria-disabled` and whether the disabled control is still a tab stop, on the component's own surface or inside the overlay its example opens: ActionSheet's disabled action, RowMenu's and Dropdown's disabled item and AlertDialog's confirm, disabled until its token is typed, each photographed in the viewport with the overlay probed beside the row, as is the overlay a hover, a focus or a press inside one is in), records a state it cannot confirm as not reached instead of photographing it, and measures each release (a press that should have been cancelled, an inspection or an overlay that does not clear become flags, named with what they mean in typed tables; a press is measured on the control pinned when it went down, so one that takes its control out of the page, as a dialog's Cancel does, is read rather than waited for, and a click that reaches the control as the button comes up after the pointer moved off counts as the press firing, since react-native-web runs `onPress` from that click, even when its handler changes nothing to see); overlays open from the web row and from the iOS and Android rows whose builds the docs inject, at every width (a drawer a component becomes only at and below a breakpoint, at those widths). The table is held to each component's own source, read statically: every press, scrub, resting-pointer handler, tab stop the web makes (every Pressable, a control role, `focusable`) and overlay it renders or opens, whether written on the element or spread onto it from a value the reader can follow, needs a recipe or an exemption whose claim is checked against that source and the page; a spread it cannot follow gives nothing. Every control the source disables (`disabled`, `aria-disabled`, an `accessibilityState`'s `disabled`, or `disabled` handed to another kit component) is read with what disables it (the props its value is true with, through local constants, and the keys of the item data it reads) and the overlay it renders inside (through a constant used there and a local component that portals its children); one an overlay is kept closed by whenever it is disabled (a Select's option rows) gives nothing. Where a rail example asks for a disabled control, by passing what disables it, the place it is in (the component's own surface, or an overlay it opens) needs a disabled recipe there, a recipe inside an overlay opening it first; a place no example asks for, and a control the component disables by itself, need nothing. A state is checked as a whole, not per element, except the overlays a component opens: each one its source renders, or hands its open state to (AvatarMenu's Dropdown, a part its platform entries inject, included), needs a recipe, and a component whose source renders more than one (the Calendar's hover card and day peek) has each recipe that opens one name it, so one overlay's recipe cannot stand in for another's. A raw primitive's rail examples are read the same way, spreads included. Each checklist's facts gain an "Interaction states" row, which says when a capture is applied inside the overlay it opens and where the source disables controls no example asks for. `bun run audit:web -- --pages` photographs every pattern and template page's first screen and each of its sections, and probes them; a section, like a state's row, is photographed with the margin its own paint needs (how far past its box the furthest shadow, outline or transform-moved box of it or anything in it reaches, cut to the clips inside it), so a card's drop shadow is not cropped, and the margin, what set each side and any side the page itself cuts are in the probe; audit pages hold infinite loops still. Every probed region records where its boxes sit in the viewport and every text the opacity that dims its ink apart from the groups it shares with its backdrop, so the analysis can find each text in its photograph. `bun run audit:analyze` reads variant cards, state shots and page sections the same way: contrast from the DOM where it resolved, and otherwise the text's painted ink over the background read from the photograph (with the colour behind a dimmed group read around it), fail-likely under 4.0 of 4.5 and review up to 4.5; type floors, small targets per region, the tree held identical across looks and surfaces, a state's own and release flags, and a state not reached with its reason. `bun run audit:calibrate` measures the photograph readings against the DOM over every family. `bun run audit:sheets` lays out per variant the card, row, device and comparison sheets, per component its states (desktop first, each tile its photograph with its flags) and per page its first screen across widths and looks, every sheet within 1600 px and cut into numbered sheets where a grid would be unreadable. `bun run audit:index` builds `.audit/current/` from the newest capture of each cell across every run, with an index per component (its cells, its states table) and per page (its cells, its sections linked one by one), and a summary ranked by flags with every state not reached and every release flag (a state cell of a recipe the table no longer has is left out with a warning, and out of the sheets); `bun run audit:prune` deletes old runs while keeping the newest two captures of every cell, then rebuilds the index so none of its links points at a deleted run. Nothing in the package changes. In the docs, the pattern and template pages wrap each section in one more View, which carries its `data-mockup-section` key on the web for the page capture; the pages look as they did.
