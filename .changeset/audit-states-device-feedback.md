The component audit's state coverage recognises a control whose only feedback for a state on a row is one the web runner cannot see: react-native-web drops `android_ripple`, so a control the source gives the ripple and nothing else that repaints a held press there (no style function reading `pressed` or `focused` that the build's skin reaches, no `onPressIn`, `onLongPress` or raw responder) shows the runner nothing on the Android row. The reader names that feedback on the control per build, evaluating the ripple's value and each style function's reads with every entry's skin; the coverage records such a press as judged on devices, never as a recipe's, and refuses a recipe applied on such a row on such a control. Dialog's and AlertDialog's press recipes are applied on the iOS row alone (their iOS capsules dim to the skin's pressed opacity), so the 12 Android cells that could only be not reached are no longer planned. The checklists' "Interaction states" row now says what the runner sets up (`recipes:`), since the facts are generated from the source with no capture, and lists under `not reachable on the web:` each state the source says the web can never show, with why: one no row of the page renders, one whose only feedback on a row is `android_ripple`, and a recipe whose field is disabled only through a TextInput's `editable`, which react-native-web renders read-only and never announces disabled (Input's and Textarea's Disabled; the recipe stays, since its cell records that finding). Repository tooling and docs only; nothing in the package changes.
